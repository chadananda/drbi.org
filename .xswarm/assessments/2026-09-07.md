# Assessment — drbi.org — 2026-09-07

Grounded the re-assessment in the repo and the live site rather than the recorded state — several recorded facts turned out to be stale.

## GOAL

The stated goal is right and I am keeping it: **drbi.org exists so that people who want to attend, enrol, or give can do so without friction, and so the Desert Rose Bahá'í Institute is never held up waiting on its website.** What I would sharpen is the timeframe. This is not an open-ended "serve the organisation" mandate for the next quarter — it has two dated obligations: *Division, Unity, and the Lord of Books* (26–29 Nov, $340/$200) and *The Dawn-Breakers Challenge* (25 Dec – 3 Jan). Thanksgiving travel gets booked six to eight weeks out, so the selling window for the first programme is **September and October**, not November. Winning, concretely, is: both programmes reach their intended enrolment, the registration numbers are visible rather than inferred, and Telahoun can publish a change without Chad.

Two corrections to the record. `project.yaml` says `stage: growth`, which is not a stage in the vocabulary the file itself defines; by its own goal this project is at **conversion** — it has reach, it has a valued action, and the action is measurable through Humanitix. And item 0004's open question is now answered: the `HUMANITIX_API_KEY` on `better-company.org` sees exactly one event, *BetterWorld 2026*. It is a different organisation. **DRBI needs its own key.**

What would falsify this: if both programmes fill through WhatsApp, the mailing list, and direct organiser outreach with negligible Humanitix referral from drbi.org, then the site is not the registration channel — it is credibility and logistics — pageloads stop being a leading indicator, and everything sequenced below is aimed at the wrong lever.

## STRATEGY

The real position is not what the backlog describes. The events system is **already built** — `src/lib/humanitix-sync.ts`, admin event editing, registrants, waitlist, invoices, announcements, a `/api/events` surface and an OpenAPI document. Item 0002 ("local events on the site") is largely done and item 0001 ("content API") is much further along than `state: ready` suggests. What is missing is not capability.

What is missing is a way to ship. **Production was last deployed 2026-08-07** — `/api/health` returns 404 in production while `health.ts` has been committed since 3 September. There are **37 commits since that deploy and 15 not even pushed to origin.** The GitHub Action that would fix this exists at `.github/workflows/deploy.yml` but cannot land: the local `gh` token lacks the `workflow` scope, and the repo has no `CLOUDFLARE_API_TOKEN`. So a month of work on the site that carries the organisation's two paid programmes is invisible to every visitor, and the only publishing route is Chad's laptop. That is the whole strategy in one sentence: **DRBI is not blocked on building, it is blocked on publishing, and the block is two credentials.**

Meanwhile the live conversion path is broken in a way that is visible right now. `/events` renders the full text of both programmes — prices, schedule, a "Registration" heading — and contains **zero ticket links**. The only Humanitix link on the site is one "Get tickets" on each detail page. Because the listing inlines the entire description, a visitor has no reason to click through, and clicking through is the sole route to buying. The same page carries **49 double-escaped entities**, so visitors read "Friday `&amp;` Saturday" and "Children `&amp;` youth" in the programme copy; the detail pages render cleanly, so it is the list-view HTML pipeline, not the source content.

I could not verify traffic — `kpi.py` returns HTTP 401, so the analytics source is unreadable today. The last recorded level was ~20–40/day and reportedly down 60% on the trailing week. That gap matters less than usual here, because the number that decides everything is registrations, and nobody is reading it.

One note on how the work gets done: the one time an agent touched production it ran `UPDATE` statements against live D1 as a diagnostic. The deploy path should be the GitHub Action, reviewed and automatic — not agent hands on production.

The engagement items (0007 newsletters, 0008 the WhatsApp calendar of fifteen prepared reveals, 0009 the Riazati newsletters) are correctly marked `class: never` and are the right work, but they are downstream. Filling a funnel whose checkout button is missing wastes the traffic.

If no — if enrolment is handled by the organisation through channels the site does not touch — then say so, and drbi.org drops to `reactive` after line 1 lands, because a site nobody is blocked on does not need a plan.
